# 3단계 — 프로젝트·인증·서버 저장

선행 조건: [2단계](./02-erd-editor.md) 완료. [공통 아키텍처](./00-scope-and-architecture.md)의 저장 계약을 따른다.

## 목표와 범위

로그인한 사용자가 프로젝트와 ERD를 관리하고, 편집한 문서를 서버에 안전하게 저장할 수 있게 한다. 동일 문서의 동시 저장은 충돌을 감지하며, 실시간 병합은 구현하지 않는다. 멤버 관리 화면과 이력 복원 UI는 6단계지만 데이터·권한 경계는 이 단계부터 적용한다.

## 구현 작업

### 1. 인증과 프로젝트 권한

- 기본 인증은 OIDC 공급자 한 개와 서버 세션으로 구성한다. issuer·client 설정은 환경변수로 제공하며 callback에서 issuer/subject를 사용자 식별자로 사용한다.
- 세션은 서비스 DB에 보관하고 HttpOnly 쿠키로 식별한다. 로그인 흐름의 state·nonce·PKCE와 쓰기 요청의 CSRF 보호는 검증한 라이브러리·프레임워크 방식으로 구현한다.
- 개발계정이 필요하면 로컬 개발·테스트 환경에서만 별도 옵션으로 제공한다. 운영 설정에서 이 우회 경로가 켜지면 시작을 거부한다.
- OIDC 실계정 설정이 없더라도 테스트 IdP나 모의 프로토콜 서버로 로그인 흐름을 검증할 수 있게 한다. 실서비스 계정 연동 여부와 로컬 검증을 구분해 보고한다.
- 프로젝트 역할은 `owner`, `editor`, `viewer`다. 프로젝트 생성자를 owner로 설정한다.
- viewer는 문서 읽기와 이미지·SQL export를, editor는 ERD 생성·수정·복제와 SQL import를, owner는 멤버·프로젝트 관리까지 할 수 있게 한다. ERD 삭제·프로젝트 삭제는 owner 권한으로 제한하는 것을 초기 정책으로 한다.
- 서버가 모든 리소스 요청에서 소속 프로젝트 권한을 확인한다. URL ID만으로 다른 사용자의 문서·이력·SQL 작업을 읽지 못하게 한다.

### 2. 데이터베이스와 마이그레이션

기본 테이블을 아래 역할로 분리한다. 실제 이름은 일관되게 정하되 책임은 유지한다.

| 테이블 | 주요 데이터 |
| --- | --- |
| `users` | 내부 ID, OIDC issuer·subject, 표시명 |
| `sessions` | 서버 세션, 사용자, 만료 시각 |
| `projects` | 프로젝트 ID·이름·생성자·시각 |
| `project_members` | 프로젝트·사용자·role, 조합 유일성 |
| `erds` | 문서 ID·프로젝트·제목·JSONB payload·revision·수정자·시각 |
| `erd_revisions` | 스냅샷 ID·문서·원본 revision·payload·종류·작성자·시각 |
| `erd_mutations` | 사용자·문서·mutation ID·요청 hash·성공 결과·만료 시각 |

- `erds`의 ID는 문서 ID와 일치한다. 목록용 제목·target 등 파생 메타데이터를 중복 저장하면 payload와 같은 트랜잭션에서 갱신한다.
- JSONB 전체를 저장하는 초기 구조로 시작한다. 조회에 필요한 프로젝트·제목·수정 시각은 관계형 컬럼과 인덱스로 둔다.
- 문서 ID와 리비전의 단조 증가·행 잠금 또는 조건부 UPDATE를 이용해 경쟁을 제어한다.
- 문서 전체 조회·저장 전에 크기와 구조를 검증한다. 작성 중인 의미 오류는 저장 가능하지만 깨진 내부 참조는 거부한다.
- 저장 payload의 문서 ID가 URL·기존 문서와 일치하는지 확인한다. 기존 문서의 target 변경은 서버에서도 거부하며, 프로젝트 소속·revision·작성자 같은 서버 관리 값을 클라이언트 payload로 덮어쓰지 않는다.
- SQL 문자열 조합으로 DB 쿼리를 만들지 않고 매개변수화한다. 서비스 DB 마이그레이션은 사용자의 DDL export 기능과 별개다.

### 3. 기본 API

| 메서드·경로 | 동작 |
| --- | --- |
| `GET /api/me` | 현재 로그인 사용자 |
| `GET/POST /api/projects` | 접근 가능한 프로젝트 목록·생성 |
| `GET/PATCH/DELETE /api/projects/:projectId` | 프로젝트 조회·이름 변경·삭제 |
| `GET/POST /api/projects/:projectId/erds` | 문서 목록·생성 |
| `GET /api/erds/:erdId` | `{ document, revision, updatedAt }` 조회 |
| `PUT /api/erds/:erdId` | `{ baseRevision, mutationId, document }` 저장 |
| `POST /api/erds/:erdId/duplicate` | 새 문서 ID로 복제 |
| `DELETE /api/erds/:erdId` | 권한 확인 후 삭제 |

에러는 `code`, 사용자용 `message`, 필요한 `details`, 추적용 request ID를 사용한다. 인증 실패·권한 실패·구조 오류·revision 충돌·용량 초과를 구분한다. 내부 stack trace·세션 정보는 응답하지 않는다.

문서 복제 시 문서와 내부 객체 ID를 새로 발급하고 모든 참조를 함께 매핑한다. 이름·타입·제약·모든 뷰는 보존한다. 프로젝트 삭제는 포함 문서 수를 보여주고 사용자 조작으로 확인한 뒤 처리한다.

### 4. 자동 저장과 경쟁 처리

- 편집 변경 후 기본 1초 debounce로 저장한다. 드래그·입력 완료 시점의 명령 단위를 기준으로 한다.
- 문서당 저장 요청은 하나씩 직렬화한다. 요청 중 새 변경은 별도 dirty 세대로 남기고 응답 후 최신 상태를 다시 저장한다.
- 응답이 왔다고 현재 편집본 전체를 서버에 보낸 옛 snapshot으로 되돌리지 않는다. 성공 응답의 revision만 해당 저장 세대에 반영한다.
- 동일 mutation 재시도는 같은 payload로 보낸다. 새 편집본에는 새 mutation ID를 발급한다.
- API는 권한 확인 후 멱등성 결과를 조회한다. 성공 결과는 트랜잭션으로 보관해 응답 유실 후 재시도가 가능하게 한다. 기본 보관 기간은 24시간이며 만료 후 오래된 base revision은 충돌로 처리한다.
- `409 REVISION_CONFLICT`면 자동 저장을 멈추고 로컬 변경을 보존한다. 서버 최신본 확인, 내 변경을 새 문서로 복제, 변경 폐기 후 다시 열기를 제공한다.
- 오래된 응답이 revision을 되돌리지 않도록 문서·요청 세대를 확인한다. 문서 전환 후 이전 요청 응답이 현재 문서를 바꾸면 안 된다.
- 네트워크 끊김·401·403·용량 초과를 일반 저장 완료로 표시하지 않는다. 복구 가능 여부와 재로그인·재시도 동작을 구분한다.

### 5. 프로젝트 화면과 임시 복구 통합

- 프로젝트·ERD 목록, 이름 검색, 수정 시각, 생성·이름 변경·복제·삭제 화면을 만든다.
- 편집기 저장 상태를 `저장 중/저장됨/저장 실패/오프라인/충돌`로 구분한다.
- 서버 조회는 문서 마이그레이션·검증을 거친다. 구형 문서가 열렸다는 이유만으로 저장 revision을 갱신하지 않는다. 실제 쓰기는 조건부 저장 계약을 따른다.
- IndexedDB 복구본을 사용자·문서·base revision으로 구분한다. 다른 계정·다른 서버 버전의 복구본을 자동 적용하지 않는다.
- 로그인 전 로컬 문서는 명시적 복구 선택 후 새 서버 문서로 옮긴다. 로그인 즉시 기존 서버 문서에 덮어쓰지 않는다.
- 서버 저장 실패·로그아웃 직전에도 미저장 내용을 잃지 않도록 복구 경로를 둔다. 브라우저 종료 시 네트워크 요청 성공을 보장한다고 가정하지 않는다.

## 검증

1. 다른 사용자의 프로젝트·ERD·mutation 성공 결과에 접근할 수 없다.
2. 두 클라이언트가 같은 revision으로 저장하면 하나만 성공하고 나머지는 409다.
3. 서버 커밋 직후 응답이 끊긴 요청을 재시도해 revision이 이중 증가하지 않는다.
4. 저장 중 추가 편집·문서 전환·지연 응답·네트워크 복구 후 변경이 사라지지 않는다.
5. 문서 복제 후 복합 FK·뷰·표현식 참조가 새 ID를 올바르게 사용한다.
6. DB 재시작 후 프로젝트·문서·리비전이 유지되고 마이그레이션이 재현 가능하다.
7. 인증·권한은 API 통합 테스트로, 생성→편집→자동 저장→새로고침은 E2E로 검증한다.

### 검증 결과

2026-11-18 Docker에서 Node.js 24.12.0, pnpm 10.11.0, PostgreSQL 17.12, Chromium 156.0.8078.79를 사용했다. lockfile 기반 클린 설치, 빌드, 타입 검사, lint가 통과했다. 기본 테스트 38개와 통합 테스트 3개가 통과했다. [API 통합 테스트](../tests/projects.integration.test.ts), [브라우저 통합 테스트](../tests/projects-browser.integration.test.ts)

| 기준 | 판정 | 확인 내용 |
| --- | --- | --- |
| 1. 사용자·역할별 접근 제어 | 통과 | 모의 OIDC 공급자에서 `state`·`nonce`·PKCE와 세션을 검증했다. 쓰기 요청은 동일 origin과 CSRF 토큰을 요구했다. 비회원의 목록·프로젝트·문서·저장 결과 조회를 차단하고, 회원이 된 다른 편집자에게도 기존 사용자의 mutation 결과를 재사용하지 않았다. viewer 읽기와 owner 삭제 경계도 확인했다. |
| 2. 같은 리비전의 동시 저장 | 통과 | 두 요청 중 하나만 리비전 2를 받았고, 다른 요청은 `409 REVISION_CONFLICT`와 현재 리비전을 받았다. |
| 3. 커밋 후 재시도 | 통과 | 서버가 커밋한 직후 HTTP 응답을 끊었다. 동일 요청 재전송 결과와 저장 상태의 리비전·시각이 일치했다. 같은 ID의 다른 요청과 만료된 저장 결과도 확인했다. |
| 4. 저장 중 편집·문서 전환·오프라인 | 통과 | 첫 저장의 응답을 지연시키고 테이블·컬럼을 추가한 뒤 다른 문서를 열었다. 추가 편집은 원본 문서에 한 번 더 저장됐다. 두 충돌 해소 경로와 오프라인 재연결, 로그아웃 후 복구, 사용자 및 기준 리비전 격리를 Chromium에서 확인했다. |
| 5. 복제 참조 재매핑 | 통과 | 복합 FK의 순서·대응과 대상 키, 뷰 배치·표시 컬럼·그룹, 식 인덱스와 조건식의 참조, enum·sequence 연결이 새 ID를 가리켰다. 복제본의 구조 검증이 통과했다. |
| 6. DB 재시작과 마이그레이션 | 통과 | 새 테스트 DB에서 초기 마이그레이션을 실행했다. PostgreSQL 재시작 뒤 프로젝트·문서·리비전과 로그인 세션이 유지됐고, 마이그레이션 재실행은 적용 이력을 확인했다. |
| 7. API와 E2E | 통과 | 실제 DB를 사용하는 API에서 권한과 무결성을 확인했다. Chromium에서 로그인 → 프로젝트·ERD 생성 → 테이블·컬럼 편집 → 자동 저장 → 새로고침 복구를 확인했다. |

## 실행과 인증 설정

- 로컬 DB는 `docker compose up -d --wait db`로 시작한다. 기본 포트는 `127.0.0.1:55432`이며 `HERD_DB_PORT`로 변경한다. `DATABASE_URL`과 `APP_ORIGIN`에 실제 DB와 브라우저 주소를 지정한다. 마이그레이션은 저장소 루트에서 `pnpm db:migrate`로 적용한다. API 프로세스 상태는 `/api/health`, DB와 초기 마이그레이션 준비 상태는 `/api/ready`로 확인한다. [환경 예시](../.env.example), [로컬 Compose](../compose.yaml), [SQL 마이그레이션](../db/migrations/001-projects.sql)
- `ERD_DEV_LOGIN=1`은 `NODE_ENV=development` 또는 `test`와 루프백 origin에서 동작한다. `NODE_ENV=production`에서는 DB 주소, HTTPS `APP_ORIGIN`과 OIDC 설정을 요구하며 개발 로그인이 설정되면 API 기동을 거부한다. OIDC는 `OIDC_ISSUER`, `OIDC_CLIENT_ID`, `OIDC_CLIENT_SECRET`과 `<APP_ORIGIN>/api/auth/callback`으로 구성한다. 검증에는 모의 OIDC 공급자의 실제 프로토콜 응답과 서명된 ID 토큰을 사용했다. 운영 IdP와 운영 계정 설정은 배포 환경에서 확인한다. [서버 설정](../apps/api/src/config.ts), [모의 OIDC 공급자](../tests/support/oidc.ts)
- 문서 저장 상한의 기본값은 20 MiB, 테이블 1,000개, 컬럼 20,000개, FK와 논리 관계 합계 5,000개다. `ERD_MAX_DOCUMENT_BYTES`, `ERD_MAX_TABLES`, `ERD_MAX_COLUMNS`, `ERD_MAX_RELATIONSHIPS`로 구성한다. `PUT` 성공 응답의 `revision`과 `updatedAt`은 같은 mutation의 재시도에서 24시간 동안 재사용된다. [저장 API](../apps/api/src/projects.ts)
- 로컬 편집과 서버 편집에는 각자의 IndexedDB 복구 저장소를 사용한다. 서버 편집에서는 계정과 문서별로 복구본을 조회하고, 기준 리비전이 다를 때 사용자가 서버본 확인·복제·폐기를 선택한다. 저장 요청이 진행 중에도 최신 편집을 복구본에 적는다. [서버 편집 세션](../apps/web/src/server-editor.ts), [서버 복구 저장소](../apps/web/src/server-drafts.ts)
