# 7단계 — 안정화와 배포 준비

선행 조건: [6단계](./06-sharing-history-and-images.md) 완료. [공통 아키텍처](./00-scope-and-architecture.md)를 기준으로 PostgreSQL MVP를 검증한다.

## 목표와 범위

1~6단계 기능을 실제 사용 규모에서 검증하고 재현 가능한 배포 패키지와 운영 문서를 만든다. 새 DBMS·새 SQL 구문·실시간 공동 편집을 추가하는 단계가 아니다. 외부 인프라 생성·유료 서비스 가입·실제 운영 배포는 별도 사용자 요청 없이 실행하지 않는다.

## 구현 작업

### 1. 사용자 흐름 검증과 회귀 수정

아래 흐름을 실제 웹·API·DB를 연결해 검증한다.

1. 로그인 → 프로젝트 생성 → ERD 생성 → 테이블·관계 편집 → 자동 저장 → 다시 열기.
2. PostgreSQL DDL 분석 → 경고 확인 → 새 ERD 생성 → 편집 → 생성 SQL 다운로드.
3. 기존 ERD에 DDL 교체 → 교체 전 버전 확인 → 복원.
4. 다른 사용자를 viewer/editor로 추가 → 권한에 따른 조작 → 권한 회수.
5. 두 탭의 동시 편집 → 저장 충돌 → 로컬 변경 복제 후 계속 편집.
6. 네트워크 끊김 → 미저장 변경 유지 → 재연결·재로그인 후 복구.

기능이 빠졌으면 해당 단계의 계약을 만족하도록 수정한다. UI 겉모양만 맞추고 검증 누락을 남겨두지 않는다.

### 2. 성능 측정과 한도

재현 가능한 seed로 다음 fixture를 만들고 총 테이블·컬럼·FK·뷰·JSON 크기를 함께 기록한다.

| 모델 | 테이블 | 컬럼 | FK | 측정 목적 |
| --- | --- | --- | --- | --- |
| 일반 | 100 | 2,000 | 150 | 편집·저장·SQL·이미지의 일상 사용 |
| 큰 모델 | 300 | 6,000 | 600 | viewport·검색·메모리·작업 취소 |

- 프로덕션 빌드, 브라우저 버전, CPU·메모리·OS, 네트워크와 DB 위치를 기록한다.
- 최초 열기·검색 이동·노드 드래그·컬럼 수정·저장 왕복·SQL 작업·메모리 사용량을 측정한다.
- 초기 목표는 로컬 테스트 환경에서 일반 모델 열기 3초 이내, 큰 모델 열기 8초 이내, 일반 모델 저장 왕복 2초 이내다. SQL 작업은 기본 10초 제한 안에 끝나거나 명확히 취소되어야 한다.
- 목표는 아직 실측 결과가 아니다. 환경상 조정이 필요하면 수치·근거·사용자 영향을 기록하고 조용히 기준을 낮추지 않는다.
- 드래그·줌 중 전체 폼 재렌더를 줄이고, 보이지 않는 노드와 접힌 컬럼을 활용한다. UI projection과 영구 catalog를 분리한 상태를 유지한다.
- SQL 작업 중 API health·문서 읽기·취소가 응답하는지 확인한다. Promise timeout만 두고 CPU 작업이 계속 도는 구현을 수정한다.
- SQL 5 MiB·문서 20 MiB 등 공통 한도의 경계값, 최대 객체 수, 초과 요청의 처리 시간을 확인한다.

### 3. 데이터·권한·실패 복구

- 프로젝트·문서·revision·SQL job의 모든 ID 경로에서 교차 프로젝트 접근을 점검한다.
- ID·이름·설명·SQL의 특수문자 입력이 HTML 실행·SQL 쿼리 조합으로 이어지지 않는지 확인한다.
- SQL 파서·worker 메모리·시간·동시 실행 제한과 프로세스 재시작 후 상태 정리를 확인한다.
- 서버 종료·DB 재시작·저장 응답 유실·작업 만료·인증 만료·권한 회수에서 복구한다.
- 오래된 문서와 snapshot의 형식 업그레이드를 fixture로 확인한다. 알 수 없는 미래 버전·확장 데이터를 임의 삭제하지 않는다.
- 서비스 DB 백업을 별도 빈 DB에 실제 복원해 문서·멤버·이력이 유지되는지 확인한다. 사용자의 DDL export를 서비스 데이터 백업으로 혼동하지 않는다.
- 자동 checkpoint·SQL job·mutation 결과·만료 세션 정리 작업의 주기와 보관 정책을 확인한다. 수동 이력의 용량 관측과 관리 방법도 문서화한다.

### 4. CI와 배포 패키지

- CI에서 설치·타입 검사·lint·단위 테스트·API/DB 통합 테스트·주요 E2E·빌드를 실행한다.
- 인증 PostgreSQL 버전은 DB 이미지 태그와 실제 실행 버전을 고정해 검증한다. 최신 태그 하나만 사용해 지원 범위를 주장하지 않는다.
- 웹·API의 재현 가능한 container build와 로컬 Compose 구성을 제공한다. DB 영구 volume·마이그레이션 실행·health check를 포함한다.
- API의 liveness와 DB를 확인하는 readiness를 분리한다. 준비되지 않은 서버를 정상 배포로 판단하지 않는다.
- 운영 환경변수, OIDC callback, 쿠키·origin 설정, SQL 한도·worker 수·TTL을 문서화한다.
- 서비스 DB 연결 정보와 사용자가 설계하는 target을 구분한다. 사용자 DB 연결 정보 입력 UI는 만들지 않는다.
- 로그는 request/job ID·상태·작업 시간·오류 코드 중심으로 남긴다. SQL 본문·문서 내용·토큰·세션 쿠키를 기록하지 않는다.
- 롤백은 애플리케이션과 DB 마이그레이션 호환성을 함께 고려한다. 새 문서 형식을 구버전 앱에 덮어쓰는 단순 롤백을 안내하지 않는다.

## 검증 기준

- 도메인 단위 테스트: 참조 무결성·명령·형식 버전·식 의존성.
- API 통합 테스트: 인증·권한·revision 경쟁·멱등성·job lifecycle·복원 원자성.
- SQL 통합 테스트: 지원 모델의 생성 SQL 실행과 DB 의미 비교, dump import, 모델→SQL→모델 비교.
- E2E: 위 사용자 흐름과 중요한 실패·복구 동작.
- 시각 검증: 테이블·관계·패널·한글·PNG/SVG 출력. 실제 파일을 열어 확인한다.
- 운영 검증: 깨끗한 환경 시작, 마이그레이션, 백업 복원, 재시작 후 복구.

이미 통과한 검사를 이유 없이 반복 확대하지 않는다. 수정한 기능과 연결된 회귀 범위를 중심으로 재검증하고, 마지막에는 필요한 통합 확인을 한 번 수행한다.
